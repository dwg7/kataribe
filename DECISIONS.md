### D2 — Dossier vs. narrative.json: split kataribe's unique work from the shared/co-developed artifact
**Date**: 2026-09-05
**What**: Settled the relationship between two things that were at risk of being conflated: the **dossier** (kataribe's own per-event document: verified facts, sources, per-layer audience/register notes, and honest caveats about what map data can and can't show — e.g. the kitavolca finding below) and **narrative.json** (the Cartographer-facing artifact: camera state + active layers + caption, per `dwg7/ferspas57`'s `NARRATIVE-FORMAT.md`).

- **The dossier is kataribe's own work, not shared.** `ferspas57` has no equivalent "backing material" concept (hfu's observation, 2026-09-05) — their narratives are authored directly from verified GAEZ/HIH data checks, with no separate richer source document behind them. Kataribe's dossier is the thing that doesn't exist anywhere else in the ecosystem yet.
- **narrative.json is the shared, co-developed artifact.** Per `staccato-spec`'s own read (session `staccato-spec-42`, 2026-09-05) and `staccato-spec`'s ADR 0009, narrative.json is an intentionally non-standardized, single-implementation vocabulary within the staccato architecture — a "cutting-edge spec" still finding its shape, not yet a spec-level guarantee. That's exactly why it's worth polishing jointly with `ferspas57` rather than forking it privately: kataribe's actual need (a *selectable* layer per question, not a *sequential* flyTo tour) is a genuinely different use case than ferspas57's own (a fixed, ordered multi-step story), and stress-testing the format against a second real use case is how a non-standard vocabulary matures toward something that could later be proposed to `staccato-spec` for real — see `CLAUDE.md`'s "not yet promoted to a methodology principle" discipline, same idea one level down at the format level.
- **Consequence**: the dossier is written once, independent of which Cartographer (`ferspas57` or `spiccato`) ends up consuming it. Each dossier layer's map state gets *projected into* a narrative.json (or a `spiccato` `#q=` link) mechanically — the projection is disposable/regenerable, the dossier is the source of truth. This also cleanly answers `staccato-spec-42`'s architectural objection (spiccato's single-Map-Intent model fits kataribe's "one question → one layer → one render" shape better than ferspas57's sequential narrative model): the objection is valid *for the projection target*, but doesn't bear on how the dossier itself is authored.

**Why**: keeps kataribe's actual point of leverage (the dossier — pre-authored, fact-checked, versioned, anti-fabrication) from becoming entangled with an unsettled cross-project format debate, while still treating the format debate as worth having (with `ferspas57`) on its own merits, per hfu's explicit framing (2026-09-05).

**Follow-up, same day — no narrative.json schema change needed after all**: proposed a `playback_mode: "sequence" | "select"` schema flag to `ferspas57-2` to distinguish kataribe's "pick one layer" need from ferspas57's sequential flyTo tours. `ferspas57-2` pushed back with the right frame (drawing a direct parallel to their own D39 language-selection precedent): *any* judgment call about which version to show a specific person belongs entirely to Staff, decided live with real conversational context, before handoff — Cartographer should never be handed more than one resolved option (this is what keeps it "faceless," ADR 0001). Applied here: kataribe's Staff reads the dossier, picks the layer, and hands over a single already-resolved narrative — exactly the same Staff/Cartographer boundary ferspas57 already draws for language choice, just one layer up. **Conclusion: no schema change.** A selected dossier layer is just an ordinary narrative (`steps: [oneStep]` if the layer is a single view; more steps only if that specific layer has its own internal build-up worth stepping through — a different question from layer-selection). The alternative case ferspas57-2 flagged — a Cartographer-page UI letting a *viewer* toggle between layers themselves, tabs-on-a-museum-placard style, with no Staff in the loop per-toggle — would be a real, different feature and *might* warrant a schema affordance, but that is explicitly **not** what kataribe wants (confirmed to `ferspas57-2` 2026-09-05): selection always happens in the Staff conversation.

**Also settled, same day — dossier content discipline**: a dossier must stay faithful to what its primary sources (GSI's document, kitavolca's actual checked tile data) directly establish — "don't awkwardly pad it" (hfu, 2026-09-05). Anything requiring a fresh/current lookup (present-day crop specifics, whether a memorial exists, this year's anniversary events) is deliberately left to narrative.json-generation time, when Staff can do real, citable research against a live source rather than freezing a guess into the versioned dossier — see `DOSSIER-FORMAT.md`'s "What belongs in a dossier vs. what gets looked up at generation time." Consequence for the first dossier: a claim like "the 1926 deposit area is farmland today" only belongs in the dossier's `facts` if it traces to the primary sources actually in hand (GSI's document as a 土地条件図 already classifies land use, or kitavolca's real VLCM data) — not because it was part of the original project-founding narrative in `HANDOVER.md`. Verify before asserting; mark `status: incomplete` rather than assume.

### D3 — Cartographer choice: `spiccato` first, `ferspas57` reserved for a future need this dossier doesn't have yet
**Date**: 2026-09-05
**What**: Settled (hfu) on `dwg7/spiccato` as the Cartographer kataribe's first dossier actually projects to, rather than forking `dwg7/ferspas57`'s narrative mechanism as originally planned in D1. `ferspas57` stays a live option for later, not ruled out.

**Why spiccato first**: (1) D2's follow-up already established kataribe's real shape is "one question → Staff resolves one layer → one resolved render," never a viewer-side toggle or an autoplayed multi-layer tour — which is structurally exactly `spiccato`'s single-Map-Intent-per-link model (ADR 0001/0004 baseline), not `ferspas57`'s sequential flyTo-tour model. (2) `spiccato` already has kitavolca's VLCM/VBM live and tested in its real catalog (`HANDOVER.md` D20, verified against `https://stars.optgeo.org/catalog` in a production-equivalent build) — `ferspas57`'s own catalog has no Hokkaido/volcano data at all, so forking it would additionally require new catalog-integration work this dossier doesn't need. (3) `staccato-spec` (session `staccato-spec-42`) independently recommended the same thing from the normative-architecture side: forking `ferspas57`'s narrative format buys no spec-level compatibility guarantee (ADR 0009 keeps it a single-implementation vocabulary), while `spiccato` gets ADR 0001/0004's baseline for free. (4) The first dossier's own `map_projection_hint` (hazard layer) is already a single camera+layer state, not a multi-step sequence — there was never an actual multi-step need to justify the heavier fork.

**Why `ferspas57` isn't ruled out**: if a *specific dossier layer* ever needs its own internal step-by-step build-up (e.g. "hazard, told as: flood-zone context → historic disaster extent → today's land use" as one guided sequence within a single layer — a different question from *which layer* to show), that is a real multi-step need `spiccato` doesn't support and `ferspas57`'s narrative mechanism does. hfu's call (2026-09-05): build on `spiccato` now, revisit `ferspas57` if/when a concrete dossier layer actually needs that.

**Consequence**: the dossier's `map_projection_hint` fields get projected into `spiccato` `#q=` links (see `dossiers/tokachidake-taisho-mudflow-1926.json`). No narrative.json is being built for the first dossier at this time.

### D4 — Converged with `ferspas57` on the Map Intent ↔ narrative.json ADR direction (via `staccato-ecosystem`/`staccato-spec`)
**Date**: 2026-09-07
**What**: `staccato-ecosystem` (coordinating with `staccato-spec-42`, ADR 0009's owner) proposed redefining `narrative.json` as a sequence of independent Map Intent documents (each optionally captioned) rather than an independently-shaped schema — Map Intent's own schema stays untouched, avoiding ADR 0009's Alternative-1 mistake (an optional `narrative` field grown onto Map Intent itself, causing step-vs-whole ambiguity). Asked kataribe and `ferspas57-2` to converge on three open points before an ADR gets drafted; both sides agreed on all three:

1. **`catalog_context`/`provenance` may duplicate across steps** (ADR 0007 Alternative 2's "reviewability over generality") rather than being hoisted to a wrapper level. `ferspas57-2`'s implementation note: with 373 existing real narratives (355 per-site + 15 tours + 3 curated) at their current lightweight per-step shape (`center`/`zoom`/`layers`/`caption` only), giving every step a full Map Intent needs real measurement of the LZString-compressed URL-length impact on longer (7–20 step) tours before implementation — not an ADR blocker, an implementation-phase item.
2. **`caption` is not redundant with Map Intent's `goal` field.** Verified against real content on both sides, independently reaching the same reasoning: `goal` and `caption` have fundamentally different speaker positions — `goal` describes what the *requester* wanted ("show Tokachidake"), `caption` speaks *to the viewer* while they're looking at the render. Kataribe's evidence: the first dossier's hazard-layer `map_caveat` field ("this polygon covers only the near-crater deposit, not the actual disaster's reach toward Kamifurano — don't let it imply otherwise") is a safety-relevant narrative statement, not a request description. `ferspas57`'s evidence: their DR Congo maize-siting narrative's "why did the constrained site score higher" mystery-caption is the same shape. Conclusion: `caption` stays a separate field; `goal` cannot absorb it.
3. **Sequence identity (`narrative_id`, step ordering) belongs at the wrapper level**, not fields inside each Map Intent step (no `step_index` etc. inside Map Intent itself).

**Why this matters for kataribe specifically**: makes D2's "a selected dossier layer is just an ordinary narrative with one step" conclusion even more literal — under this direction, a single-step case may not need a narrative wrapper at all, just a bare captioned Map Intent. Also validates `DOSSIER-FORMAT.md`'s `map_caveat` field design after the fact — it turned out to be exactly the content point 2's convergence needed, not a kataribe-specific idiosyncrasy.

**Status**: convergence reported to `staccato-ecosystem-85` 2026-09-07; ADR drafting is `staccato-spec-42`'s next step, not kataribe's — no action needed here until an ADR draft is circulated for review.

### D1 — Repo founded: a dossier-based narrative Staff, general-purpose, first instance is 十勝岳大正泥流
**Date**: 2026-09-05
**What**: Created `dwg7/kataribe` (public, CC0 1.0) at hfu's request, made during a `dwg7/staccato-ecosystem`-session Claude Code conversation, following an ecosystem-growth-strategy discussion that identified `dwg7/kitavolca` (Hokkaido volcano data pipeline) and `dwg7/kaga0` (air-gapped Cartographer appliance) as mature Library/Cartographer-side work with no matching Staff. A design proposal (drafted by a `model: fable` subagent, reviewed by hfu) settled three core design calls: (1) audience is "local intermediaries" only for v1 (disaster-prevention staff, teachers, tourism/onsen operators — not GSI-internal, not general public), framed as strengthening the accountable human chain; (2) a place/event's significance is multi-layered (hazard, livelihood, place-identity, ...) and Staff's job is recognizing which layer a specific asker needs, not covering all of them — to be validated here before being proposed as a `staccato-ecosystem` methodology principle, not before; (3) "lowering the bar" (pre-authored, versioned dossiers) is the primary constraint-workaround, even more heavily than `dwg7/ferspas57` used it — Staff selects and adapts register/language, never originates facts live.

**Naming**: `kataribe` (語り部, "one who carries a memory forward across generations, retelling it for whoever is listening") chosen over a volcano-specific name (hfu considered and rejected "volkataribe" — both because it reads awkwardly and because the repo is explicitly general-purpose; volcano is only the first domain, not the scope).

**First dossier**: 十勝岳大正泥流 — the 1926-05-24 Tokachidake mudflow disaster. Chosen partly because 2026 is its 100th anniversary, and partly because it's a near-perfect illustration of the layer-selection concept: the same land is simultaneously the 1926 hazard site and, today, farmland — disaster and livelihood are literally the same physical deposit at different points in time. Primary-source material (GSI's 1990 火山土地条件図「十勝岳」explanatory document) gathered the same day — see `HANDOVER.md`.

**Cartographer plan**: fork/adapt `dwg7/ferspas57`'s narrative-playback Cartographer mechanism (flyTo + layer-sync + caption panel, ADR-0004-compliant one-shot fragment handoff) rather than build one from scratch — but treat its actual JSON schema as something this repo has discretion to reshape, not a fixed contract to replicate (hfu's explicit call, given `ferspas57`'s own narrative format is itself still mid-revision). Verified the same day that `ferspas57`'s `main` branch still runs an older design (10-language pre-baked content) than a newer one (English-only, Staff does live adaptation) sitting unpushed in another session — coordinated directly with that session (`ferspas57-2`) rather than assuming either state.

**Why**: matches the established `dwg7` pattern — dedicated repo, dedicated session, `HANDOVER.md`/`CLAUDE.md` as onboarding (see `dwg7/staccato-ecosystem` D1, `dwg7/ferspas57` D1). hfu's own reasoning for placing this in the `dwg7` org from the start, rather than a personal-namespace prototype stage first (as `DWG7-CONTEXT.md`'s convention would otherwise suggest for early experiments): the underlying concept — 火山防災 grounded in official GSI/disaster-prevention-agency data — is already publicly and institutionally established, not a personal hobby project, so it doesn't need a "prove it's legitimate" prototype phase.
